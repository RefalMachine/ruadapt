# Обобщение стратегий packing для CPT и SFT

Обсуждение реализовано: sequence overflow (split/drop/truncate/error), strategy
(none/whole/dense), isolate и tail (pad/drop/keep) доступны в конфиге. Актуальная
семантика и ограничения описаны в [документации](../docs/PACKING_AND_ATTENTION.md).
Ниже сохранено исходное предложение, включая описание состояния до реализации;
его открытые вопросы не следует трактовать как описание действующего кода.

Задача — независимо управлять обработкой длинных примеров, плотностью укладки, изоляцией attention и последним неполным pack. Одинаковые настройки должны применяться к CPT и SFT. В частности, нужны возможность отбрасывать длинные документы CPT и возможность плотно упаковывать данные с изоляцией без padding в полных packs.

**Текущее поведение**

- CPT isolated нарезает документы длиннее pack на фрагменты. Короткие документы и полученные фрагменты укладываются целиком.
- SFT отбрасывает диалоги длиннее `sft.max_tokens_count` после применения chat template. До токенизации также работает грубый фильтр по числу символов: больше `max_tokens_count * 4`. Он может исключить диалог, который по токенам поместился бы.
- Укладка isolated общая: последовательный алгоритм без перестановки примеров. Если следующий пример не помещается, текущий pack закрывается. Поиска меньших примеров для заполнения свободного места нет.
- Collator isolated дополняет каждый pack до `packing.max_length`, затем объединяет логический микробатч из B packs в физическую строку `[1, B * L]`, сохраняя границы сегментов.
- Явный режим CPT stream плотно заполняет packs, разрезая документы на их границах, без изоляции документов. Финальный хвост сохраняется. Старый путь CPT без секции packing отличается обработкой хвостов.
- SFT без packing сохраняет один диалог одной строкой батча; при dynamic padding строки дополняются до максимальной длины в батче с учётом `pad_to_multiple_of`.

Исходники: [общая укладка](../ruadapt/training/datasets/document_packing.py), [подготовка SFT](../ruadapt/training/datasets/sft_factory.py).

**Предлагаемая обработка длинных примеров**

```json
"sequence": {
  "max_length": 4096,
  "overflow": "split"
}
```

Лимит применяется до укладки к документу CPT или полному токенизированному диалогу SFT, включая chat template.

| overflow | Поведение |
|---|---|
| split | Нарезать слишком длинный пример на последовательные фрагменты |
| drop | Исключить слишком длинный пример целиком |
| error | Остановиться с понятной ошибкой |

`truncate` с потерей хвоста можно добавить отдельно, только как явно выбранный режим. Окончательная необходимость этого варианта не обсуждена.

**Предлагаемая укладка и изоляция**

```json
"packing": {
  "strategy": "dense",
  "max_length": 4096,
  "isolate": true,
  "tail": "drop"
}
```

| strategy | Поведение |
|---|---|
| none | Один пример или подготовленный фрагмент — один семпл |
| whole | Укладывать примеры целиком, закрывая pack, когда следующий пример не помещается |
| dense | Заполнять pack до конца, при необходимости разрезая очередной пример на границе pack |

`whole` сохраняет нынешний последовательный алгоритм isolated. Это не сортировка и не поиск оптимального заполнения.

Обработка overflow и нарезка при укладке имеют разный смысл: первая ограничивает длину исходного примера, а `dense` может разрезать даже короткий пример ради заполнения остатка pack. Например, `overflow=drop` исключает слишком длинные исходные документы, но не запрещает делить оставшиеся при dense packing. Для сохранения целых примеров выбирается `whole`.

Для `whole` необходимо валидировать совместимость лимита примера с размером pack. Для `none` параметры изоляции между упакованными примерами и хвоста не применяются; точное правило проверки таких конфигов ещё нужно определить.

`isolate=true` задаёт независимый causal attention между документами или диалогами внутри pack. Границы передаются через метаданные сегментов либо соответствующую маску attention. Padding между сегментами для изоляции не нужен. Позиции сбрасываются на начале каждого сегмента, target первого токена сегмента маскируется.

При `isolate=false` внутри pack действует обычный causal attention, включая переходы между документами. Смысл этой настройки не должен зависеть от выбора attention backend; неподдерживаемые сочетания должны явно отклоняться.

**Пример укладки**

Размер pack — 4096. Примеры A, B, C имеют длины 3000, 2000, 3192 токена соответственно.

```text
whole:
pack 1: [ A:3000 ][ PAD:1096 ]
pack 2: [ B:2000 ][ PAD:2096 ]
pack 3: [ C:3192 ][ PAD:904  ]

dense:
pack 1: [ A:3000 ][ B1:1096 ]
pack 2: [ B2:904 ][ C:3192  ]
```

При dense isolated A и B1 не видят друг друга; B2 и C также изолированы. B2 не видит B1, поскольку они находятся в разных семплах. Нарезка на независимые окна теряет предшествующий контекст независимо от изоляции внутри pack. Перекрывающиеся окна или перенос состояния были бы отдельной функциональностью и в это предложение не входят.

**Последний неполный pack**

| tail | Поведение |
|---|---|
| pad | Сохранить и дополнить до размера pack |
| drop | Отбросить неполный хвост |
| keep | Сохранить с фактической длиной |

При dense неполным остаётся только последний pack в рамках одного прохода упаковки. Остаток нужно переносить через внутренние батчи обработки данных, чтобы не создавать и не терять хвост на каждом батче токенизации.

`dense + tail=drop` даёт только полные packs без padding. `dense + tail=pad` допускает padding только в последнем pack. `keep` требует поддержки переменной длины collator и выбранным backend: varlen допускает переменную суммарную длину, а прямоугольное представление батча может потребовать дополнения. Поэтому отсутствие padding нельзя обещать для любого backend и collator лишь по значению `keep`.

При whole незаполненные packs возможны и в середине датасета. Настройка tail относится только к последнему pack и не устраняет внутренние пустоты. Возможная передача всех whole packs без дополнения — отдельное решение о представлении батча.

**Сочетания режимов**

| Сценарий | overflow | strategy | isolate | tail |
|---|---|---|---|---|
| Классический плотный CPT | split | dense | false | drop |
| Плотный CPT isolated | split | dense | true | drop или pad |
| CPT с исключением длинных документов | drop | dense или whole | По выбору | По выбору |
| SFT без packing | drop | none | Не применяется | Не применяется |
| SFT с сохранением целых диалогов | drop | whole | true | pad |
| Плотный SFT isolated с нарезкой | split | dense | true | drop или pad |

**Особенности SFT и loss**

Единица изоляции SFT — весь диалог, а не отдельная реплика. Внутри диалога assistant видит предшествующие сообщения по обычному causal attention. По умолчанию loss считается на assistant targets; user и system остаются контекстом с замаскированными labels.

При нарезке SFT маска labels переносится вместе с токенами, но ответ может продолжиться в следующем pack без исходного вопроса. Это меняет учебную задачу, поэтому нарезка должна быть явно выбрана пользователем.

Фрагменты могут содержать только контекст и не иметь обучаемых targets. Перед реализацией нужно определить обработку packs и целых шагов с нулём targets, включая распределённую нормализацию loss. Автоматическое удаление таких фрагментов не следует вводить незаметно: оно меняет состав данных и может противоречить обещанию сохранения токенов.

**Общий механизм и открытые решения**

Предлагаемый порядок: задача готовит `input_ids` и `labels`; общий обработчик применяет overflow и укладку; collator представляет результат для выбранного attention backend. Выбор SDPA, FA2 или FA3 не должен менять состав packs, границы примеров и смысл loss. Фактическая поддержка определяется возможностями backend, модели и установленного стека.

До реализации нужно согласовать окончательные имена настроек и дефолты, совместимость старых конфигов, взаимодействие с `sft.max_tokens_count`, обработку грубого символьного фильтра SFT, packs без targets, правила для eval и допустимые сочетания лимитов. Текущие настройки и поведение существующих запусков пока не меняются.
